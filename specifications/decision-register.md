## Established direction

- The command center is a personal first-stop system for understanding today's work, upcoming commitments, and links to longer-term goals.
- Separate stable data, views and workflows, and visual presentation.
- Prefer centralized data and filtered views; do not duplicate task databases by timeframe or life category without a strong reason.
- Favor a minimal, fast, maintainable, Notion-native system. The listed features are candidate direction, not a frozen scope or detailed design.
- Preserve user data. Avoid automatic deletion, destructive schema changes, duplicate object creation, and overwriting meaningful content. Keep secrets out of code.
- Plan and approve product, UX, data, workflow, automation, visual, and technical decisions before building.

## Decision sequence

The order follows dependencies. A later category can reopen an earlier choice, but the conflict must be resolved and recorded.

### 1. Product boundaries and success — decided

- P01: First-stop Home for today's work, upcoming commitments, and connection to longer-term goals; Home content is specified below.
- P02: All personal life areas from the start, with the seven initial Areas specified in the schema.
- P03: Quick status with optional planning and on-request AI.
- P04: Daily upkeep target is 5–10 minutes; acceptance includes a realistic time trial.
- P05: Start fresh; no existing Notion data to migrate.
- P06: AI prompting through both ChatGPT/Codex and Claude is the primary way to add or change records. Structural changes follow a versioned dry-run/update path. Actual client permissions are verified at implementation setup.

### 2. Daily, weekly, and monthly experience — decided

- X01: On request through a prompt or navigation action, AI proposes the daily Top 3 for user confirmation. Unfinished choices are reconsidered tomorrow; intraday replanning is explicit. Home shows Top 3, Calendar, then up to two weekly priorities.
- X02: Weekly review every Sunday and separate monthly review on the last calendar day, even when both coincide. AI prepares summaries when requested; user confirms proposed changes. Missed reviews remain available without overdue review Tasks. Content is specified in the working specification.
- X03: End-of-day check is optional, with an AI summary on request and a manually opened view. One-task Focus has no timer; interruption capture goes to Inbox.
- X04: Compact Home and Quick Add are the primary desktop/phone entry points. Acceptance checks verify both layouts and the 5–10 minute daily flow.

### 3. Information architecture — decided

- I01: Compact Home and dedicated Tasks, Projects, Goals & Areas, Notes, and Habits & Reviews destinations; Focus opens from a Task; full Inbox is reachable from Home; Start Here is a small linked guide.
- I02: Home primary order Top 3, Calendar, up to two weekly priorities; secondary order Inbox with Quick Add, Active Projects, Progress Metric. Calendar includes actual appointment titles/times through a private managed mirror.
- I03: Inbox is the unprocessed Capture Queue; Backlog, Someday, Completed, and other work queues are filtered views of central databases.
- I04: The minimum views, filters, and sorts are listed in schema-and-views.md.

### 4. Core data architecture — decided

Add Calendar Events as a tenth, read-only managed display cache solely to put Apple Calendar appointments on the custom Home page; it is neither a Task database nor a second appointment source of truth.
- D02: Task, Project, Goal, Area, Note, Capture Queue, Planning Log, Habit, Habit Check-in, and Calendar Events fields, types, conditional requirements, and identity rules are specified in schema-and-views.md.
- D03: ATLAS chain approved as Tech Career Area → "Gain skills and broaden personal portfolio" Goal → ATLAS parent Project → flexible Phase child Projects → Tasks. Relationship cardinalities and phase readiness are specified in schema-and-views.md; only the user confirms closure.

- D05: Start fresh with no migration; Notion Tasks own work, Apple Calendar owns appointments, and Calendar Events is a managed display cache.

### 5. Object lifecycles and capture — decided

- L01: Quick Add stores raw input in Capture Queue. AI processes Inbox only on request; pending count appears on Home and Sunday review. Clear direct AI requests may create records directly; uncertain captures remain Needs clarification. Quick Add is native, while Process Inbox opens the connected AI route.
- L02: Task statuses, Backlog/Someday, subtask, recurrence, and dependency rules approved. Completed and Cancelled tasks are retained with completion/cancellation history. Deferring a task changes Plan date, not Due date unless the real deadline changes. AI may update a task on explicit request and summarizes the change.
- L03: Project lifecycle uses Planned → Active → Paused/Done/Cancelled as appropriate. Clear Definition of done before Active; user confirms Done. Preserve completed/cancelled projects and phase history.
- L04: Goals remain flat and move through Planned, Active, Paused, Achieved, Dropped. Monthly review assesses evidence against the horizon; only user confirms Achieved.
- L05: Notes and Brain Dump go to Notes or Capture Queue. Convert a Note into a Task only on explicit request or after confirmation of an AI suggestion; preserve the source Note.

### 6. Calendar and time — decided; local sync feasibility gate remains

- C01: Apple Calendar has mixed or uncertain backing accounts. Notion Calendar is the combined live viewer; a private local Mac sync populates the custom Home's read-only Calendar Events mirror with appointment title/time only. Calendar inclusion is selected during setup. Home shows last sync and a link to live Notion Calendar.
- C02: Task Due date is the real deadline; Plan date is a flexible intended workday; an optional time block is a confirmed start/end interval. Moving a Plan date or time block does not change Due date.
- C03: Apple Calendar remains appointment source of truth, Tasks remain Notion work source. Never duplicate appointments as Tasks or silently move appointments/deadlines. The Home mirror can be stale while the Mac is off, so mobile has a live Notion Calendar link and last-sync indicator.
- C04: AI may suggest selective time blocks; user confirms. Time blocks belong to Tasks and may be shown in Notion Calendar, without filling the entire day.

### 7. Habits and reviews — decided

- H01: Habit definition has Name, Area, cadence (daily, selected weekdays, or N times per week), Active/Paused/Archived, and optional start date. Each check-in is a separate dated record with Done/Excused state, optional note, and idempotent Habit+occurrence identity. Binary completion is default; numeric amount/unit may be added only for a habit that needs it. Paused time and Excused occurrences are excluded from eligible opportunities. Favor recent consistency over streak pressure.
- H02: Daily Planning Log may hold optional review; Habit Check-ins are separate so daily planning may be skipped without losing habit history.
- H03: Daily review is brief and optional; Sunday and month-end review content and confirmation rules are specified in the working specification. Exact prose is a content-writing detail, not an unresolved product decision.

### 8. Metrics and feedback — decided

- M01: Home Progress Metric is weekly Top 3 follow-through, displayed as completed of confirmed daily Top 3 choices in the current Monday–Sunday week. Deeper views show project phase status/readiness, Goal evidence, habit consistency, and operational Inbox/Waiting counts. No composite productivity score.
- M02: Exclude days with no confirmed Daily Plan; use final confirmed Top 3 after explicit replanning and record the change. Show the raw numerator/denominator, not a percentage alone. A completed task counts for its planned day only if marked Done by that day's end in `America/Vancouver`, respecting daylight saving time.
- M03: Compute task and habit counts from records; Goal evidence and Project/phase completion require human confirmation. Do not derive a project's outcome from task count.

### 9. Buttons, automation, and AI — decided; client capability gate remains

- A01: Use a small set of native quick actions: Quick Add to Capture Queue, mark a Task Done, open a Task's Focus view, record a Habit check-in, and open the current review. "Mark Waiting" must collect a reason; do not leave a one-click action that creates invalid Waiting records. The "Plan my day," "Process Inbox," and AI review entry points should open clear prompt guidance or a connected AI surface; do not label a button as if it invoked AI when it only opens a page. Use templates for Tasks, Projects/phases, Goals, Notes, and review logs, with prefilled structure but little mandatory input.
- A02: Keep simple navigation, quick capture, task status, and habit check-ins native to Notion. Use both connected ChatGPT/Codex and Claude clients for on-request triage, planning, summaries, and natural-language edits, governed by one shared behavior/schema guide. Use a separate API integration only for capabilities that the native client cannot reliably perform. A deterministic local Mac service handles the required Apple Calendar → Notion display-cache sync and any recurring Task series that native templates cannot safely generate. No background AI; scheduled AI is optional later and needs plan/cost review.
- A03: AI reads the structured system, proposes Top 3 and weekly/monthly decisions, and applies explicit routine single-record edits, including Plan date or Priority changes, then reports them. It must show proposed changes for confirmation when choosing daily/weekly priorities, changing Committed/Someday state, changing real Due dates, routing ambiguous captures, or closing Projects/Goals. For a broad edit, show a concise scope and dry-run preview. AI instructions limit reads/writes to command-center pages; hosted MCP workspace authorization may still grant broader access, so the user should choose a private workspace or review accessible content at setup. The user can work manually if an AI client is unavailable.
- A04: Every automation or AI write uses an identity key or existing Notion ID, checks before creating, and is safe to retry. On partial failure, report which records changed and which did not; never silently repeat a create operation. Keep a small activity log for setup/updates and batch AI operations. Recurrence uses independent occurrence records, with a stable series+date identity; a native repeating template may be used only when it meets the same duplicate and date behavior.

### 10. Visual design and accessibility — recommended design approved under standing approval

- V01: Use a calm, minimal native Notion aesthetic: Default font at normal size, short section headings, ample spacing between the three primary blocks, thin dividers only where needed, and no large Home cover. Use a simple consistent icon set for destinations, with at most one icon per heading or page. Color is semantic and sparse: neutral for ordinary work, blue for planning/navigation, amber for Waiting/attention, red for approaching or missed real deadlines, and green for confirmed Done. Do not use color to denote permanent priority alone. Respect light/dark mode and avoid hard-coded image backgrounds.
- V02: Home has a single readable vertical primary sequence on both desktop and mobile: Top 3, Calendar, weekly priorities; then Inbox, Active Projects, Progress Metric. Display only a few records and link to deeper views. Desktop may use modest width and adjacent small controls where mobile order remains clear; avoid wide tables on Home. Dedicated database pages may use denser tables on desktop and compact list/board views on phone. Do not use paid-plan Dashboard view as a prerequisite.
- V03: Every signal has text as well as color/icon: status names, due dates, pending counts, and phase readiness labels. Use descriptive link/button labels, sufficient contrast, and no essential information hidden in a cover, emoji, chart, or hover-only control. Test both light and dark appearance and phone stacking before acceptance.

### 11. Technical design and safety — decided; setup capability gate remains

- T01: The user now has the free individual Education Plan, equivalent to Notion Plus. Build the core with native pages/views/buttons and on-request connected AI. Plus permits database automations and unlimited charts; use a small number of native automations where they reduce manual work, and keep charts in deeper views rather than making Home depend on them. Business-only Dashboard views and Custom Agents remain out of scope. Plus does not include ongoing Notion AI beyond limited trial use. Verify the workspace's actual plan, eligibility, and integration access before any write. Use the current supported Notion API version at implementation time, subject to a compatibility check; the current views API supports creating, listing, and updating views. Database button actions cannot be created/configured through the public API, so their UI setup and verification are an explicit delivery step. Follow Notion rate-limit and size-limit responses rather than fixed sleeps. Verify the actual connected AI client can read/write the necessary page, database, and view objects before promising prompt-driven changes.
- T02: Keep the product specification, schema manifest, view definitions, and workflow/AI rules in version control. Keep Notion database, data-source, property, view, template, button, and page IDs in a separate environment-specific manifest. Setup discovers existing objects by ID first, then checks scoped names/keys before creating. Dry-run is default for structural updates and prints a human-readable change plan; apply mode requires an explicit command. Repeated runs converge without duplicate objects. Layout definitions can change without recreating data stores. Schema migrations are additive by default and versioned.
- T03: Store secrets in environment variables or the user's secret manager, never in the repo, logs, or Notion pages. Before a structural change to populated data, capture a schema snapshot and export the affected data, and verify the export exists. Keep a periodic manual export reminder in the monthly review, with a clear note that export is an archive, not an instant relational restore. Log object IDs, operations, and failures without sensitive page bodies. Respect `Retry-After`; after ambiguous write failures, read current state before retrying. Validate relations, required conditional fields, unique period/occurrence keys, view filters, and a sample of records after each update. Provide a recovery runbook for partial setup or failed migration. Never auto-delete databases, pages with user data, or properties; destructive changes need a separate approved migration.
- T04: Develop against mocked API fixtures and a dry-run plan first; then make a small isolated smoke test in the chosen Notion workspace or a disposable test workspace if available. Record the actual Notion plan, API version, permissions, and unsupported UI actions in the handoff. Keep the schema manifest and implementation under version control, with a change log and a short maintenance guide. User-requested layout changes should touch views/pages only; data-model changes use a reviewed migration with a rollback/restore path.
