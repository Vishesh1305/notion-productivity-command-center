# Setup and recovery

## Prerequisites

1. Select the intended private Notion workspace and parent page. Record their IDs in ignored `manifest.json`. Confirm the same workspace is selected before every live write.
2. Create a Notion internal connection through **Settings → Developer → Open developer tools**, enable read/insert/update content, and grant it access to the private Productivity Command Center parent through **Content access → Edit access**. Store its API token in macOS Keychain with `macos/store-notion-token.sh`. At the Terminal `password data for new item:` and `retype password for new item:` prompts, paste the token; the helper rejects an empty item. Do not paste the token into chat or a project file. A second AI client's connection requires its own read/write check.
3. Preserve ignored `manifest.json` and never commit it. For another workspace, copy `manifest.example.json`, supply a private parent page ID, and review the dry-run before applying.
4. Run `PYTHONPATH=src python3 -m command_center.cli plan`. If using the direct API route, run `inspect` next. An isolated smoke test and private production structural setup passed through the connected Notion client.
5. Run `apply` explicitly for future additive changes. It creates only missing pages/databases/properties/views. Repeat `inspect` and `apply`; the second apply should report no changes. A type conflict or duplicate scoped name stops the run. Before adding properties to a populated source, an ignored `exports/` snapshot is written and verified.
6. The approved starter Areas and example Project/Goal chain are defined in code. `seed` is retry-safe by name and should add nothing on a clean rerun.

## Apple Calendar mirror

1. Run `calendars` on the user's Mac. The `macos/calendar-export.sh` wrapper builds a read-only Objective-C EventKit bridge and macOS requests full Calendar access. The bridge contains no Apple write calls. If the prompt times out or access is denied, grant CalendarExport access in macOS settings and retry. The alternate Swift source is currently blocked by a compiler/SDK version mismatch.
2. Select calendars explicitly and save only their IDs in the ignored manifest. Holiday and birthday feeds are excluded unless deliberately chosen. A complete read-only export with real events passed on 2026-10-25.
3. The direct `macos/run-job.sh sync-calendar` passed with nonempty event data. Timed Start/End values use Vancouver's local offset so Notion's date picker shows local time. Existing event instants were verified against a private pre-change snapshot, and a second sync made no event updates. Check that notes, location, invite details, and attendees are not copied.
4. The direct Notion integration token remains in the user's macOS Keychain under service `notion-command-center`. The `macos/run-job.sh` wrapper reads it at run time without putting it in launch arguments or version control. `macos/install-jobs.sh` installed three user-level LaunchAgents from the reviewed `.plist.example` files on 2026-10-01, after their one-shot checks passed. Calendar starts at login and repeats about every 15 minutes; recurrence starts at login and runs at 07:00 daily; follow-through metric refresh starts at login and repeats hourly. All first launches exited 0. Keep job logs private.
5. A failed or partial Apple read must leave existing events active and keep the prior successful-sync time. If Home shows stale data after 30 minutes, use live Notion Calendar for current appointments. Do not propose time blocks as if the mirror is complete.

## Recovery

- Re-run `inspect` before any repair. A known ID wins; a unique scoped child name is the fallback. Resolve duplicate names manually before applying.
- If a write times out or returns a 5xx, read the target by key/name before retrying. The client does not automatically replay ambiguous writes.
- If a schema change is needed, preserve the `exports/` snapshot and compare row counts plus source properties. Additive `apply` never deletes existing properties, pages, views, or rows. Destructive migrations require a separate reviewed script.
- For a Calendar failure, inspect permission, selected calendar IDs, and the last sync health record. A healthy rerun upserts by occurrence key and can recover from partial Notion writes.
- `habit-checkin HABIT_ID YYYY-MM-DD` records an eligible Done check-in; use `--status Excused`, `--amount`, or `--note` where appropriate. An exact rerun returns the same page, including a page made by the native button; conflicting entries require review. `habit-report HABIT_ID START END` reads the existing check-in and pause events and reports raw done/eligible counts plus duplicate or incomplete-pause warnings. Both commands require the direct Notion integration. The native check-in button's live setup-record test passed; the direct CLI route remains to be tested after Keychain setup.
- For recurrence, retain existing occurrences. The generator only creates today through fourteen days ahead and does not backfill missed past dates.
